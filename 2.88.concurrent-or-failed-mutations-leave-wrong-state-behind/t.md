# concurrent or failed mutations leave wrong state behind

Nothing serialises yman processes on one clone. `add` reads the taken-id set once (add.rs:94), and its only collision check is `dir.exists()` on the full `priority.id.slug` name. Two `yman add` started together, such as an agent's parallel tool calls, therefore mint the same id, and `sync` only renumbers local-vs-remote collisions. Every mutation also writes, stages, then commits. When the commit fails (`commit.gpgSign` with no usable gpg, a held `index.lock`), nothing is unstaged, so the next successful command commits those paths under its own subject. A retried `add` mints a new id and duplicates the task, and `attach` has already printed `attached …` on stdout. `rm` rewrites and stages the other tasks' `related` before `git rm -rq`. When `git rm` refuses a folder with local edits, the command exits 1 with the dropped references staged, which is the exact state rm.rs:28-30 promises never to produce.

- Where: src/commands/add.rs:94, src/commands/add.rs:124, src/commands/add.rs:202, src/commands/set.rs:208, src/commands/attach.rs:124, src/commands/tags.rs:135, src/commands/state.rs:49, src/commands/rm.rs:31
- Done when: 8 parallel `yman add` give 8 distinct ids, each in its own commit; with `commit.gpgSign=true` and `gpg.program=false`, `yman add X` exits 1 and leaves a clean `yman git status --porcelain`; and `yman rm -f 1` with task 1 hand-edited either removes it or leaves task 2's `m.yml` byte-identical.
