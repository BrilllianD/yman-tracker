# sync: a clean merge can publish a task split across two folders

`duplicate_ids_gate` runs only under `sync --continue`, so a merge that completes cleanly but leaves two folders for one id is committed and pushed. After that, every clone fails `find` with `duplicate task id`. Two triggers reach that state. First, `rejoin_split_folders` warns and leaves the old folder holding only `f/`. `task_dirs` still counts that folder as a task, and `a_left_behind_file_is_not_moved_over_an_existing_one` asserts this state as correct. Second, renumber and merge read `refs/yman/remote` by name after its sha was pinned at sync.rs:402, so a concurrent `git fetch` (refspec appended by init) brings in ids that were never renumbered. Rejoin and drop also run only in the invocation that made the merge. If anything fails after the merge commit lands, the next sync sees `base == remote` and skips them, and `snapshot_dirty` commits the half-staged moves.
